# RepoRescue v0.3.0-alpha.1

Package version: `0.3.0a1`. JSON schema: `0.2`. Extension API: `1`.
These versions describe separate contracts. This is an experimental alpha release.

## Highlights

RepoRescue evolves from a single Python diagnostic tool toward an extensible
project recovery foundation, following **Small Core, Large Ecosystem**.

- Experimental public Extension SDK and Pack model, with an official synthetic example.
- Explicit Pack registration and controlled discovery of installed Pack factories.
- Python diagnostics routed through the common built-in Extension Pipeline.
- Windows Python 3.12 / 3.13 CI, Pack hardening tests, and Windows interpreter
  long-path / 8.3 short-path identity fixes.

Python remains the only real built-in language Pack. Ordinary CLI diagnosis stays
built-in only; repair previews and verification plans are not executed.

## Extension SDK

Pack authors should import from `agent_doctor.sdk`. The facade re-exports selected
Core models, metadata and capability protocols without duplicating their types.
`EXTENSION_API_VERSION = "1"`; API v1 is experimental during v0.3 and does not
promise permanent compatibility.

The [SDK guide](https://github.com/furX7/RepoRescue/blob/main/docs/extension-sdk.md) covers public imports, metadata, capabilities,
registration, discovery and limitations. The
[official example Pack](https://github.com/furX7/RepoRescue/blob/main/examples/extensions/example_language_pack.py) uses
only the public SDK and Python standard library. It observes a synthetic marker
and produces evidence, a diagnosis, and descriptive plans; it is not loaded by default.

## Pack Architecture

A Pack groups domain knowledge through Detector, EvidenceProvider, DiagnosisRule,
RepairPlanner and Verifier contracts. Packs supply observations, diagnoses,
repair proposals and verification plans.

Core owns orchestration, compatibility checks, safety policy, consent, resource
limits and execution authority. `PackRegistry` validates explicit instances before
inserting them, rejects duplicate IDs, and preserves registration order. Pipeline
compatibility checks filter API, platform and required-tool mismatches.

The default registry contains only `python.core`. The common pipeline dispatches
capabilities without adding language-specific workflow branches. See the
[architecture documentation](https://github.com/furX7/RepoRescue/blob/main/docs/architecture.md).

## Controlled Discovery

Hosts can explicitly call `discover_installed_packs(registry)` to query installed
Python distribution entry points in the fixed group **`reporescue.packs`**.
No-argument factories return Pack instances for registration.

Discovery ordering is deterministic. Ordinary query/load/factory/validation
failures are isolated; duplicate IDs never replace an existing Pack, including
`python.core`. Process-control signals propagate. Declared pipeline failures use
fixed messages rather than copying third-party exception text.

There is no filesystem scanning, network lookup, automatic installation or
automatic CLI discovery. Importing the SDK does not trigger discovery.

## Safety and Trust Boundary

**Installed third-party Packs are executable Python code.** Loading an entry point
imports code, and calling its factory executes code. **RepoRescue validation is
not a sandbox. Only load Packs from sources you trust.**

The SDK does not provide a Core CommandExecutor, arbitrary shell authority or
repair execution authority. Third-party Python can still import standard-library
or other APIs and cause its own side effects; metadata validation cannot prevent this.

Default diagnosis does not execute project code. `--run-startup-probe` remains an
explicit opt-in for the supported root-level `main.py` probe, with existing safety
checks, timeout and bounded startup output capture. Executed project code may have
file, network or service side effects. Reports may contain local paths and sensitive
captured output; review them before sharing. See [SECURITY.md](https://github.com/furX7/RepoRescue/blob/main/SECURITY.md).

## Compatibility

- Windows First; Python `>=3.12`.
- The pre-release baseline passed GitHub Actions on Windows / Python 3.12 and
  Windows / Python 3.13. Local validation uses Python 3.13.1.
- No runtime dependencies.
- CLI commands and existing Python diagnostics remain available.
- JSON schema remains `0.2`; Pack/registry/discovery metadata is not added to reports.
- Package version `0.3.0a1` and Extension API `1` are versioned independently of JSON.

## Known Limitations

- Experimental alpha and Extension API v1; not a complete plugin ecosystem.
- Python is the only real built-in language Pack. No Node, Java, C/C++, Docker or
  Framework Packs, and no separately verified Linux/macOS support.
- No automatic CLI discovery, marketplace, installer, enable/disable management,
  dependency resolver or priority system.
- No sandbox, process isolation, generic secret masking or process-tree supervision.
- Repair and verification are planning-only; no execution, transactions or rollback.
- No GUI, LLM or Agent/MCP integration. Startup still supports only root-level `main.py`.

## Upgrade Notes

Ordinary CLI users upgrading from v0.2.x need no migration: commands are unchanged,
current diagnostics remain available, and JSON schema remains `0.2`. The report's
tool version reflects the new package version.

The Extension SDK is new and experimental. Pack authors should use the public
facade, keep declarations stable, test their capability implementations, and load
trusted Packs explicitly. Installing a Pack does not make the normal CLI load it.
